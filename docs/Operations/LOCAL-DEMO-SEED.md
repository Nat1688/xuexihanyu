# DS-01 local demo

DS-01 seeds a newly provisioned, disposable PostgreSQL database named
`clp_demo_ds01`. It refuses `clp_dev`, `clp_test`, hosted addresses, production
runtime and URL query/fragment overrides. It never loads `.env` or falls back to
`DATABASE_URL`. Use an explicit loopback IP and port.

## Provision and run

1. Provision a separate PostgreSQL 17 instance bound only to loopback, with a
   new local test role. Use password authentication for any persistent demo.
   Do not reuse a cluster with user data. Have Owner approve its location/port.
2. Create the new `clp_demo_ds01` database in that instance. Apply the repository's
   existing migrations to that new database with Prisma `migrate deploy`.
   DS-01 adds no migration and performs no automatic schema operation.
3. In PowerShell, enter the URL without saving it in the repository:

   ```powershell
   $env:DEMO_DATABASE_URL = Read-Host 'Disposable PostgreSQL URL (loopback IP, explicit port, clp_demo_ds01, no query)'
   $env:DEMO_SEED_CONFIRM = 'DS-01_DISPOSABLE_ONLY'
   $env:DATABASE_URL = $env:DEMO_DATABASE_URL
   npx --no-install prisma migrate deploy
   npm run demo:local:dry-run
   $demoSecret = Read-Host 'New demo password (16-128 characters)' -AsSecureString
   $demoPointer = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($demoSecret)
   try {
     $env:DEMO_PASSWORD = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($demoPointer)
     npm run demo:local
   } finally {
     [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($demoPointer)
     Remove-Item Env:DEMO_PASSWORD -ErrorAction SilentlyContinue
   }
   ```

Use a password unique to this disposable demo, never a real account password.
All seven synthetic accounts use this operator-supplied password at creation.
Only salted scrypt hashes are persisted. Reruns do not change existing hashes;
providing a different password on a rerun does not rotate passwords.
The dry run validates target configuration but opens no connection and needs no
password. Unknown CLI arguments exit 2. Refusal/seed failure exits 1; success 0.
Raw database errors, URLs, passwords and row content are not printed by the CLI.

## Dataset and ownership

| Rows                                  | Count / ownership                          |
| ------------------------------------- | ------------------------------------------ |
| Synthetic identities                  | 7, in `example.invalid` only               |
| Published course / units / lessons    | 1 / 2 / 3; authored by `teacher.one`       |
| Chinese learning items / lesson links | 13 / 13                                    |
| Class                                 | 1, owned by `teacher.two`                  |
| Enrollments / assignments             | 2 / 6, for `student.one` and `student.two` |

Logins are `teacher.one@example.invalid`, `teacher.two@example.invalid`,
`student.one@example.invalid`, `student.two@example.invalid`,
`admin@example.invalid`, `student.pending@example.invalid`, and
`student.disabled@example.invalid`. The last two cannot log in. The admin has
ADMIN only; teachers have TEACHER only; students have STUDENT only.

Internal fixture UUIDs are deterministic and scoped to DS-01. Public UUIDs are
random UUIDv4, as required by current APIs, and stable across reruns.
Existing login/slug collisions with non-DS-01 IDs abort the entire transaction.
Old synthetic seed accounts are not silently adopted or overwritten.

The seed never searches learning items by matching Chinese text. Existing demo
items must match fixture content and author; changes cause conflict, not a rewrite
of history-bearing content. Non-demo items with identical text are untouched.
Demo publication can be restored and missing enrollments recreated. Existing
enrollment timestamps and due dates are preserved. Due dates may therefore age.
Role/state drift causes refusal instead of account repair. No evidence, mastery,
sessions, submissions, teacher notes, AI or media rows are generated by seeding.

## Demo use

Run the existing API and SPA against this disposable database, using the normal
configuration contract and newly generated local session/CSRF secrets. Configure
`DATABASE_URL` and `POSTGRES_*` consistently for the disposable instance; do not
copy production or Main `.env`. Start API/SPA only when you intend to run the demo.

As `student.one`, use Login → Today → Exercise → Result → Next. Learning evidence
is generated by actual answers, not fabricated by the seed. CP-05 recovery uses
the authenticated, CSRF-protected POST endpoint after reload/partial failures.

There is no Teacher Web UI. Authenticate `teacher.two` via `POST /auth/login`,
then use the issued session cookie for `GET /teacher/classes`, the class roster,
student assignments and progress endpoints. State-changing requests require the
session's CSRF cookie plus `x-csrf-token` header. Content author `teacher.one`
does not own this class and cannot read its roster. Students cannot use Teacher APIs.
Do not paste cookies or credentials into tickets or source files.

## Verification and recovery

`npm run demo:local:verify` now runs real PostgreSQL + HTTP integration tests.
Owner approved replacing the incomplete memory harness; its original source
remains preserved in Legacy. It is not imported and no memory test is presented
as PostgreSQL evidence.

Verification requires a **fresh migrated database**, using the same explicit
`DEMO_DATABASE_URL` and confirmation above. Run verification before manual
seeding, or in a separate disposable instance. It refuses populated fixtures,
does not reset data, generates its own temporary random password and leaves
synthetic rows for inspection. Verification-created accounts are not intended
for interactive login because that random password is not printed. Use another
fresh instance with your supplied password for an interactive demo.

Tests cover rollback after identities/content/assignments, existing user/course
collision refusal, repeated/concurrent seed, identical-text non-demo items,
credential/date/ID stability, publication recovery, real login, Student answer
evidence/mastery, Teacher ownership, roles and CSRF. Pure guard/fixture tests run
in the normal API suite. Missing target means the integration suite is skipped;
the explicit verification command instead fails if no safe target is supplied.

Every seed runs in one transaction with a transaction-scoped advisory lock on
the same connection. Failure rolls back the whole seed. On a network timeout,
rerun: committed rows retain their identities and timestamps. No automatic
deletion, reset, destructive repair, cleanup or database-drop path is provided.
For a changed/colliding dataset, preserve it for review and provision a separate
disposable instance; do not delete conflicting rows to force the seed through.

Loopback checks and a confirmation string prevent accidental targeting; they are
not proof that a database contains no real data. Provisioning and approval remain
the operator's responsibility. Temporary trust authentication is for isolated
test instances only; stop them after verification. Keep database files outside
Git and protect them with local filesystem permissions.
