# ENROLL-01 — Self registration and course admission

Checkpoint: additive CORE-01 enrollment. Owner approved 30/10/2026: immediate STUDENT login after signup; apply to a course; Admin approves any / teacher only own course and own destination class; reviewer selects class; approval required for ALL students including existing accounts. Existing data/accounts/history retained, but old students need course approval too.

Objective/scope: Vietnamese registration/login UI, course catalog metadata, per-course application with pending/approved/rejected/cancelled states, student status/history, teacher/admin scoped review queue and class choice. Approval transaction grants course access and upserts existing class membership atomically. One live pending/approved application per student/course; terminal decisions immutable, rejected/cancelled requests may be resubmitted. Reviewer/time/class/reason recorded. Course-to-class association is recorded on approved application; a class can serve multiple courses, preserving existing assignment model. Only published courses accept requests. No self-selected elevated role.

Architecture/contracts: modular monolith; identity owns signup, admissions module owns application decisions and exports course-access application service. Auth/session/current roles, scrypt, CSRF remain authoritative. Course metadata remains discoverable; lessons/items/exercise issuance/resume/answer access require approval server-side for STUDENT. Teacher/Admin keep existing authoring/read privileges. Raw item library is Teacher/Admin only; student items are read in approved lesson context. Existing result/history data remain intact. Enrollment by invitation/manual roster alone cannot bypass course admission. No automatic grant/backfill to old students.

Persistence: additive migration 11 creates course_applications, status enum, FK/indexes, partial unique live-request constraint and decision consistency checks; no changes/deletions to existing rows. Migration tested on fresh and ten-migration fixtures before live consideration. Never edit migrations 1–10. Passwords only hashed through existing identity boundary; no email verification/delivery, payments, public infrastructure, AI, password reset, notifications, account editing, existing account credentials, commit/push/merge.

Allowed: admissions module; identity signup service/controller/module; content/student/classroom course-access integration; related web screens/api/workspaces; schema and migration11; tests/docs/deployment compatibility only where required. No redesign of unrelated UI.

Acceptance/tests: new signup cannot supply ADMIN/TEACHER role, invalid/duplicate input/rate limits/origin enforced; unauthorized/unapproved course reads and exercises denied; metadata visible; apply/reapply/duplicate/cancel; cross-student and cross-teacher access denied; Admin any / teacher own; invalid class/refused student/duplicate decisions cannot partially enroll; approval grants course+class atomically. Actual GUI signup/apply/review/reject/approve/study tested using synthetic accounts on isolated PostgreSQL. Targeted tests → independent review/fix → full regression/build → docs. Live account acceptance without passwords stays PENDING_OWNER_MANUAL_TEST.

Owner decisions resolved; task implements them without guessing authorization. Deployment requires fresh encrypted backup and additive migration compatibility evidence; no reset/restore of live DB. Report exact files/tests/migrations and any remaining gate.

Deployment recovery clarification from independent review: previous API lacks admission enforcement. After migration begins, failure stops API/Web and preserves DB/evidence; do not reopen old unrestricted API. Only pre-migration failures may recover old images. This enforces Owner’s newly approved access rule. No DB rollback/reset.
